## Explicitly deferred

- Timed sales and bidding are not exposed through the API.
- Buyer and seller dispute submission is not exposed through the API.
- Descriptive business-profile fields alone do not indicate seller identity or business verification; only the reviewed verification lifecycle does.
- Cross-channel email, SMS, and push delivery for discovery or other marketplace events remains deferred to the durable notification-provider implementation; P0-16 delivers saved-search matches only to the protected in-app notification store and P0-19 must honor conversation mutes.
- Message attachments remain disabled until the hardened media pipeline provides metadata stripping, decompression protection, malware scanning, review hooks, lifecycle rules, and orphan cleanup.
- Real-time conversation updates and delivery/read-state reconciliation remain deferred to P0-20.
- Post-payment cancellation, refund, partial refund, chargeback, release, and compliance-hold inventory policy remains deferred to the payment-state implementation rather than being inferred from incomplete payment semantics.
- Reserved schema objects for still-deferred capabilities do not indicate product availability.
- Reintroduction requirements are defined in `DEFERRED_MARKETPLACE_FEATURES.md`.

## Current protected marketplace journey

1. A visitor browses active listings and opens a public item page without authentication.
2. Catalogue searches can combine text, category, condition, availability, price/currency, text location, fulfilment, an approximate nearby centre/radius, and deterministic newest/price/nearest sort controls on web or mobile.
3. Nearby search quantizes the buyer-supplied centre to a `0.01` degree privacy grid, uses PostGIS geography operations, excludes listings without an approximate point, and returns only coarse whole-kilometre distance rather than seller coordinates or exact metre precision.
4. Pagination uses a filter-bound opaque cursor so a cursor cannot be replayed with different filters, radius, centre, or sort order; distance cursors order by distance/date/identifier while legacy timestamp cursors remain accepted only for newest-first results.
5. A user registers or signs in with email or an explicit international phone number. Phone input is canonicalized to E.164 before uniqueness checks, rate limiting, lookup, or persistence; local-only numbers are rejected rather than assigned an assumed country.
6. Every account receives a private marketplace profile row. Public profile data remains unavailable until the owner explicitly saves public visibility.
7. A newly registered account requests a code for its configured email or phone. Only a HMAC-bound code and contact fingerprint are persisted; codes expire after 10 minutes, are single-use, and are subject to durable issuance and attempt limits.
8. Successful contact confirmation records the channel verification time and activates a pending account. Web and mobile registration hand off directly to the protected verification flow.
9. Signed-in users can edit profile, business, location, and privacy fields. Public profile responses never contain email or phone and independently respect city, country, business-detail, and avatar visibility.
10. Sellers can open the protected seller-verification screen. The API derives individual-seller versus business level from the current profile, requires an explicit country code, and creates or resumes one serialized provider-hosted verification context.
11. Provider results are authenticated with a dedicated signed-event contract and durable replay ledger. Passed, failed, and manual-review results remain pending at marketplace level until an account holding `verification.review` makes the final audited decision.
12. Approved seller verification receives an explicit expiry date. Expiry or a material verified-business-name change requires reverification. Mobile uses the exact localized secure seller-verification page when browser human verification is enabled and never places credentials, account IDs, verification IDs, or provider data in the handoff URL.
13. Owners can maintain a signature-validated avatar, generate a JSON account export, or enter the password-confirmed closure/deletion workflow. Mobile uses the exact localized secure profile page for browser-specific avatar/export operations without embedding credentials or account data in the handoff URL.
14. Account closure hides the profile, removes eligible seller listings, cancels pending buyer offers, revokes refresh sessions, and invalidates outstanding recovery/verification challenges. Deletion additionally anonymises reusable contact/login/profile identity while retaining opaque marketplace records required for transaction and audit integrity.
15. If a user forgets a password, the public recovery endpoint accepts email or phone and gives the same accepted response regardless of account existence. Existing eligible accounts receive a 20-minute opaque reset token while PostgreSQL stores only its HMAC digest.
16. Consuming a valid reset token changes the password, invalidates every outstanding reset token, revokes all refresh sessions, and prevents token replay. Signed-in users can instead change their password after confirming the current password, with the same all-session revocation policy.
17. Signed-in users can review active refresh sessions, revoke one owned session, or revoke all sessions from web or mobile.
18. Access and refresh credentials move into protected session storage appropriate to the client.
19. Administrative access is derived from active PostgreSQL role assignments on every protected operations request. Moderation queue reads/resolution, listing changes, account changes, seller-verification review, audit reads, and role management are separate permissions rather than one operations-wide privilege.
20. The first platform administrator is created once from a trusted deployment shell. Later role grants/revocations require `roles.manage`, reject self-role changes and privilege escalation, retain assignment history, and write protected audit records. Moderation-only staff cannot suspend an account that carries an active administrative role.
21. Sellers create listing drafts through a challenge-bound form. In challenge-enabled deployments, images are added afterward so each upload receives its own media-specific verification.
22. Draft, active, and expired listings can be opened in an owner-only edit form covering category, title, description, price/currency, condition, availability/quantity/unit, privacy-safe text location fields, and pickup/delivery options. The form submits the version it loaded; an intervening listing update returns `409` and requires an explicit reload rather than overwriting newer state.
23. Sellers can separately configure or clear an owner-only approximate listing point. The API quantizes it to `0.01` degrees, the database rejects more precise points, and the write uses the same listing `edit_version`, status gating, challenge action, no-op handling, and stale-write protection as other listing edits.
24. Public catalogue, listing detail, saved/watch/recent, and discovery-notification responses never expose the stored point. Location-update audit metadata records only whether a point is configured, not its coordinates.
25. Mobile performs detail and approximate-location edits natively when browser verification is disabled. When verification is enabled, the app opens only `/{locale}/sell/manage/{listingId}/edit` and never puts access credentials, account data, edit versions, challenge values, coordinates, or form fields into the URL.
26. Active listings have an explicit expiry date. The lifecycle worker expires due listings, expires their still-pending offers, writes audit records, and advances the same listing version used by optimistic seller editing.
27. Sellers can review expiry and inventory on web or mobile. An active listing can renew only inside the configured renewal window, while an expired listing can reactivate when it still has publishable inventory; renew/reactivate uses the loaded listing version and rejects stale state with `409`.
28. Finite goods have non-negative durable inventory. Legacy omitted finite quantities normalize to one unit, zero inventory maps to `out_of_stock`, and service listings remain quantity-unlimited with a `NULL` inventory count.
29. Sellers preview draft and published galleries through owner-only URLs, add images up to the eight-photo limit, and delete individual images unless the listing is sold or removed.
30. Mobile sellers can preview those same owner-only galleries. Native upload and deletion run only when challenge verification is disabled; otherwise the app opens the exact localized secure photo manager without placing credentials, listing IDs, or challenge values in the URL.
31. Mobile binary uploads inherit access-token refresh and one-retry session behavior while preserving the original bytes and protected content type.
32. Buyers can start the listing conversation or submit one idempotent pending offer.
33. Sellers review incoming offers and atomically accept or reject them.
34. Accepting an offer creates a durable inventory reservation. Finite goods reserve and decrement one unit; service listings create a zero-quantity reservation. The existing marketplace transaction model still reserves the listing and rejects competing pending offers.
35. When the final finite unit is reserved, the listing becomes `out_of_stock`. The accepted-offer reservation has a bounded pre-order deadline; an order cannot bind it after that deadline even if the lifecycle worker has not yet swept it.
36. Buyers may cancel only pending offers or create one order from an accepted offer.
37. Order participants, amount, currency, payment method, and listing are derived from persisted records rather than client input.
38. Order creation atomically binds the accepted offer's inventory reservation and establishes one payment intent plus one fulfilment record without collecting funds.
39. Buyers may irreversibly cancel eligible unpaid orders. Cancellation releases the reservation, restores exactly the finite unit that was reserved, cancels the accepted offer, synchronizes the payment context, and returns the listing to active only when its expiry is still valid.
40. Accepted offers that never become orders are released by the lifecycle worker after their reservation deadline; finite stock is restored and the abandoned accepted offer becomes expired.
41. The lifecycle worker is a separate supervised process (`worker:listings`) and uses a PostgreSQL advisory lock plus bounded `FOR UPDATE SKIP LOCKED` work so duplicate workers do not apply the same sweep concurrently.
42. When an approved provider integration is configured, a signed and time-bounded `payment.held` event may atomically move only a matching pending order and eligible payment intent to paid/held.
43. Payment-event retries are accepted only when the provider event identifier and semantic payload match the durable replay ledger; conflicting replays are rejected.
44. Buyers and sellers can open participant-only order history, detail, and payment-context views with lifecycle progress.
45. Eligible sellers can mark readiness for pickup or submit bounded shipment evidence on web or mobile after verified held payment.
46. Eligible buyers can confirm receipt on web or mobile, with an explicit notice that confirmation does not release funds.
47. Mobile native fulfilment mutations run only when challenge verification is disabled; challenge-enabled environments open the exact secure web order for browser verification without placing mobile credentials in the URL.
48. My Listings loads only that seller's records and exposes editing, approximate-location, status, media, and expiry/renewal/inventory lifecycle controls through owner-bound APIs.
49. Messages lists only conversations where the account is a participant.
50. Conversation threads load protected history, acknowledge reads, and send idempotent challenge-bound messages.
51. A user may mute one conversation without affecting message eligibility. The mute is private to that user and persists for future notification delivery policy.
52. A user may block the conversation counterpart. Either-direction blocking stops new messages for the pair, blocking auto-mutes the blocker's existing conversations with that account, and existing participant history remains readable.
53. Customer conversation responses expose `blockedByMe` and generic `messagingAvailable`; they never reveal whether the counterpart was the party who created a block.
54. Message sends are serialized with block mutations and durable sender-history checks. Repeated same-pair content, repeated cross-recipient content, and excessive new-counterpart velocity are rejected before persistence, while a database trigger independently prevents blocked/non-participant writes.
55. Message attachments remain a zero-item contract until the hardened media pipeline exists. Web and mobile show the policy and do not expose an upload control.
56. A participant can report an incoming message. The client sends the message UUID, reason, and optional details; conversation and reported-user identity are derived from persistence, and reporting one's own message or another conversation is rejected.
57. Message reports enter the existing moderation queue. An authorised reviewer can inspect only the report-linked target-centred conversation context, including retained removed-message statuses and participant safety state; the access is permission-mapped and audited.
58. Expired access sessions rotate automatically and retry the protected request once.
59. Signed-in buyers can independently save or watch an active listing. If a referenced listing later becomes unavailable, discovery lists retain only a removable reference and do not expose inactive listing details.
60. Opening an active listing while signed in records a bounded recently viewed relationship with first/last view timestamps and a per-listing view count.
61. Web and mobile catalogue users can save the current normalized filter set, including an approximate nearby centre/radius, as a named search. Semantically identical filters are unique per account and do not persist pagination cursor or sort-only presentation state.
62. A saved search starts matching from its creation time rather than sending a backlog of existing listings. Re-enabling a paused search resumes from the current time, and changing its filter definition resets the cursor and removes alerts generated for the previous definition.
63. The discovery worker matches new or updated active listings using the same text/category/condition/availability/price/currency/text-location/nearby-radius/fulfilment semantics as live catalogue search, excluding the search owner's own inventory and suspended/closed sellers.
64. Saved-search matches create durable in-app notifications with read/unread state and per-search/listing deduplication. Web and mobile users can acknowledge one alert or mark all saved-search alerts read.
65. The discovery worker is a separately supervised process (`worker:discovery`) using a PostgreSQL advisory lock, bounded saved-search batches, `FOR UPDATE SKIP LOCKED`, and an ordered `(updated_at, listing_id)` checkpoint so equal-timestamp listings are not skipped at a batch boundary.
